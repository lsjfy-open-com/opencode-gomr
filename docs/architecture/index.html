GOMR 当前架构讲解

Goal-Oriented Memory Runtime: 用目标路由的 rebuilt context 替代累积上下文。

1. 总体架构：GOMR 是 OpenCode 的本地上下文运行时

当前设计不是 GraphRAG，也不是自动长期记忆演化系统。它更像一个本地、确定性的上下文控制层：记录行动状态，按当前目标选择材料，生成 rebuilt context，并在默认 replace 模式下替换 provider 请求里的旧对话历史。

2. 请求替换链路：从用户目标到 provider payload

默认模式是 GOMR_MODE=replace。它不会再把 GOMR 信息“额外注入”到原始上下文后面，而是在 provider 请求层把旧消息历史替换成 rebuilt context 加最新用户轮次。

1

捕获当前目标

插件从最新 user message、session title、prompt 等位置提取目标，并过滤掉泛化的 current OpenCode task。

2

刷新 context plan

contextPlan(project, goal) 写入 turn snapshot、latest path、ledger 当前目标，并触发 route。

3

构建 rebuilt context

buildContextForRequestGoal 生成带 raw_context_replaced: true 的 Markdown。

4

重写 provider messages

保留原始 system 和 tools，移除旧 user/assistant/tool 历史，只附加 GOMR context 与 active turn。

5

工具执行后沉淀证据

tool.execute.after 记录 tool trace、ledger、context state，并刷新 visual。

Provider messages

效果

4. 路由算法：静态图 + Goal-conditioned PPR + Bundle DAG

当前路由完全确定性：先构建 bounded static repo graph，再根据目标词、PPR、状态、新鲜度、重要性、backtrack 和 penalty 打分，最后取前 12 个材料并组合成 context bundles。

Static Repo Graph

扫描 README、docs、src、tests、.opencode、.codex、package.json 等文本材料。

当前已经加了保护：跳过 binary assets / lockfiles，只读前 64KB，mention 边每节点最多 8 条，避免大项目 OOM。

Goal Router

routeGoal 读取 graph，做 personalized PageRank 与本地评分；项目理解 / project understanding 这类 overview 目标会优先 README、docs、package 等概览材料，并惩罚 tests。

一般目标评分

score = .45*ppr + .20*lexical + .15*state + .10*freshness + .05*importance + .05*backtrack - penalties

适合“实现 adapter”“修测试”“改 runtime”这类代码工作目标。

项目理解目标评分

score = .55*overview/lexical + .20*importance + .10*freshness + .05*state + .10*ppr - penalties

用于避免大项目里测试文件因图结构传播而压过 README/docs。

5. 设计分析：优点、风险和下一步

当前架构已经从“把 GOMR 文本注入上下文”转向“真正替换原始历史”。这解决了上下文膨胀的方向性问题，但后续质量取决于路由、观测和可验证性。

已经做对的部分

replace 是正确主线：如果 rebuilt 只是额外添加到原始历史上，GOMR 就不会压缩上下文。现在的 provider rewrite 已经从根上避免了这个问题。

可回溯性不错

ledger、trace、route、debug context 都落盘。出问题时可以问：目标是什么，选了什么，排除了什么，最终发送了什么。

路由质量仍是核心风险

确定性路由稳定、便宜，但语义理解浅。复杂项目里，“看起来相关”的文件仍可能被选错，需要更多语义结构或显式任务边。

维度当前状态主要风险建议
Context 压缩 默认 replace，发送 rebuilt context + active turn。 active turn 中如果工具结果过大，仍可能变大。 继续做 active turn tool-result 摘要或大输出替换。
Token 统计 基于可测文本和 telemetry 的估计。 provider tokenizer 与 OpenCode 内部包装仍可能造成偏差。 保留 telemetry import，并把 provider observed prompt tokens 与 GOMR estimate 分开展示。
Repo Graph bounded static graph，跳过 assets/lockfiles。 仅靠 tags/mentions，缺少真实 AST dependency。 Graphify adapter 或语言级解析器可作为增强输入。
Visual 默认 compact Bundle DAG，full graph 在 debug。 如果 graph-data 本身过大，浏览器仍要加载。 后续可拆分 data：compact data 默认加载，debug graph 懒加载。
OpenCode 集成 插件 hook + fetch wrapper。 依赖 provider request shape；OpenCode 更新可能破坏。 增加 request rewrite fixture 测试与版本兼容探测。

推荐下一阶段

把 GOMR 从“可用的 deterministic runtime”推进到“可校准的 context controller”：每次请求都产出一个 compact debug record，包含 raw estimate、rebuilt estimate、provider observed prompt tokens、selected bundles、hidden/excluded counts。

一句话架构判断

当前架构方向正确：它把上下文管理从“对话越来越长”改成“目标驱动的本地证据重建”。真正要继续打磨的是路由质量、观测闭环、以及大项目下的懒加载与语义边。
